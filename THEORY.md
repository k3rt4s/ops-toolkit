# ops-toolkit theory

What a session needs to believe before it changes this repo's scripts or tests.

## Invariants

- Every state-changing script writes `<prefix>-yyyyMMdd_HHmmss\` with a CSV and JSON per report plus `summary.json`. `scripts\reporting\Compare-OpsToolkitRun.ps1` can only diff that exact layout; changing it breaks the diff tool silently.
- A check that could not run is never folded into a pass. The evidence pack records actual populations, exclusions, artifacts, freshness, and limitations; source-read failures never masquerade as endpoint counts or framework conformity.
- Every state-changing script is tested as a pair, `-WhatIf` and executing (`tests\Integration.StateChanging.*.Tests.ps1`); "`-WhatIf` changed nothing" is unfalsifiable alone, a broken script passes it too.

## Load-bearing constraints

- The scheduled-task host is Windows PowerShell 5.1, which reads a BOM-less file as the ANSI code page and fails to parse it silently, so the task still reports success. `Invoke-RepoValidation.ps1`'s Encoding gate (~line 252) fails any script with non-ASCII bytes and no BOM; `??` and `?.` are pwsh-7-only for the same reason.
- One non-standard comment-based-help keyword silently invalidates the entire help block; `Get-Help` falls back to generated syntax with no error. The Help gate (~line 300) catches this now; `.INSTRUCTIONS` hit 30 of 31 scripts before it did.
- Live WMI and WUA reads can block indefinitely while Windows Update orchestration is busy. Live integration setups use `Invoke-ScriptUnderTest -TimeoutSeconds`; expiry tree-kills the child and reports `NotRun`, because an absent result is not a pass.
- Report and rollback writes, and the run directory itself, carry `-WhatIf:$false` on purpose: writing the plan *is* the preview, not the change being previewed. Without it, `Resolve-Path` throws and a `-WhatIf` run produces nothing to review. A run directory is never reused: a same-second run of the same prefix gets `_2`, `_3`, so code that picks runs by name goes through `Get-OpsRunDirectory`, which sorts by timestamp and then that suffix.
- A Graph field that exists only in beta returns `$null`, not an error, as `servicePrincipalCredentialKeyId` and `defaultMfaMethod` (`scripts\entra\`) both did. Check a new field against the installed SDK model type before trusting it.
- The evidence pack starts each collector with `Start-Process pwsh -File` (`Invoke-Collector`), which passes every argument as a literal string: `-X a,b` binds the one string `a,b`. So a list reaches a collector as one comma-joined value it splits with `ConvertTo-OpsSplitList` (`OpsToolkit.Reporting`), called right after the import, only when bound, in every script declaring `[string[]]$ComputerName`; a test enforces it. `Export-CloudIncidentReadiness.ps1` keeps an identical copy a test lifts from its AST. Anything else resolving a target list (the pack's `-TargetListPath`) must split the same way or reported and queried scope diverge. People hit it too: `pwsh -File x.ps1 -Target A,B` hands a `ValidateSet` the one string `A,B`, so doc examples use `pwsh -NoProfile -Command "& '.\x.ps1' -Target A,B"`.
- `New-Item -Force` on a registry key that already exists replaces it, wiping its values and subkeys. Every registry write creates a key only after `Test-Path` says it is missing; `-Force` inside that guard only creates missing parents.
- A rollback file is found by its exact timestamped name, never `<prefix>-rollback-*.json`: that wildcard also matches the `-rollback-plan-` file a `-Rollback` run writes, so the next rollback would replay a plan.
- Hardening rollback validates the whole file before planning, also under `-WhatIf`, against the control tables the forward plan uses, so they cannot drift; a refused file changes nothing. The newest file is chosen by name and renamed `.consumed-<ts>.json` only after an executing run where every item is `Reverted` or `NoChange` (WDAC also `Met`), so repeated rollbacks walk back one run each. An unrestorable prior (unknown, Exploit `NOTSET`) is `NoChange` with a note. The BitLocker file carries no key path.
- `Test-WindowsHardeningState.ps1`: `Unread`, `ReportOnly`, `Precondition` and `NotCheckedRemotely` are non-verdict states outside `ItemsChecked` that keep `Passed` false; a legacy-plan row it cannot classify (Skipped, a service, Missing) is `Unread`. The default `-Target` stays `SchannelTls,Privacy`; the evidence pack passes all twelve as one comma-joined value `-Target` splits (a `ValidateScript` for that reason) and grades CFG-01 from `UnreadCount` and `Passed`.
- No hardening script is verified on a real machine; `windows-hardening\VDI_RUN_SHEET.md` lists what to confirm (`hard-elevated-run`). WDAC enforce is its own script with its own rollback; the audit base never enforces. A BitLocker startup PIN is refused on any VM and exists only as a SecureString. ASR rules go in one by one (`Add-MpPreference`), so foreign rules survive. BitLocker escrows every new protector before `Enable-BitLocker`; no usable key destination refuses the run before any change.
- Host and settings facts come from one shared module, `modules\OpsToolkit.Hardening` (`Get-OpsHostContext`, `Get-OpsOrgSettings`), imported by relative path, never copied per script, so detection cannot drift; any copy elsewhere (infosec `windows_hardening\`) keeps that layout. Session hosts fail closed: an unread host type is treated as an AVD session host for anything that could cut off other users (RDP, inbound firewall rules, NTLM denial).
- `Invoke-PlanItem` carries its script's `ConfirmImpact = 'High'`, so a live run prompts per change and anything unattended must pass `-Confirm:$false`. An unelevated `-WhatIf` returns `Previewed` only for an item whose value was read; an unread one is `Skipped: requires elevation (not read)`, since the checker counts `Previewed` as Drifted.
- The IIS header scripts write `customHeaders` and `removeServerHeader` at the site path, into that site's own `web.config`, so a deployment that replaces `web.config` silently removes them; re-run after deploys or put them in the app's `web.config`. Native HSTS (`-UseNativeHsts`) lives in `applicationHost.config` and survives. Only the external checkers prove `removeServerHeader` works.
- `Test-ExternalSecurityPosture.ps1` runs its sweep on load, so a test cannot dot-source it. Finding rules that need tests go in `OpsWebCommon.ps1` as pure functions (`Get-OpsWebHeaderHygieneFinding`), and `WebSecurityReview.Tests.ps1` reads the sweep's finding catalog from its parse tree to check every key the helper returns exists.

## Decisions that look wrong

- The shared test stub (`tests\TestHelpers.psm1` ~line 295) shadows `Microsoft.PowerShell.Management` cmdlets but deliberately excludes `Get-Process`, `Start-Process`, `Stop-Process`: scripts use them to find their own interpreter or read `reg.exe`'s exit code, and a global stub would break them, not protect the machine. Real-process tests stage a local fixture instead.
- `ScheduledTasks`, `Defender`, and `PrintManagement` cmdlets are not covered by that stub trick, because a same-named function only shadows commands from its own module. Trusting it once disabled four real scheduled tasks and added three real Defender exclusions on the dev machine. Fixed with staged fake modules at `tests\Fixtures\FakeSystemModules\`, loaded ahead of the real ones, plus a `MachineState` gate in `Invoke-RepoValidation.ps1` that snapshots Defender exclusions, tasks, printers, and drives around the test run and fails on drift. Since 2026-10-29 it also snapshots ASR, firewall, BitLocker, code integrity, SMB1, LSA, audit and lockout state.
- Under `pwsh -File script -WhatIf`, ConfigDefender and ConfigCI fail to load (their import-time `Set-Alias` is suppressed), and a function-local `$WhatIfPreference = $false` does not help; only `$script:WhatIfPreference = $false` around `Import-Module -Global`, restored in `finally`, works (real-module probe 2026-11-02; thirteen other modules load fine). `Invoke-OpsWindowsScriptPair`'s `& script` does not reproduce it, so such tests start `pwsh -File`, and any test that does must point every system binary at a fake (`-DismPath`, `-CiToolPath`).
- On Windows 11 client SKUs, `Set-ProcessMitigation` can return success for system DEP and SEHOP and store nothing, so Exploit reads every mitigation back before calling it Applied. The DISM cmdlets fail under pwsh 7, so feature and AppX work goes through dism.exe with timeouts. Credential Guard is opt-in and edition-gated, so the checker reports "neither configured nor running" as `ReportOnly`, never drift.
- Mutation recorders pass `-WhatIf:$false`, or the recorder's own `Add-Content` inherits the caller's `-WhatIf` and a "nothing changed under `-WhatIf`" assertion cannot fail; a fake declares `SupportsShouldProcess` only where the real cmdlet does and records only inside it. Stubs for reads (such as `pip cache dir`) answer unrecorded, so only writes count as mutations. A function defined in a test's ExtraSetup does not shadow a cmdlet a fake module exports; vary a fake's behaviour through an environment hook it documents (`OPSTOOLKIT_TEST_CI_IGNORE_OPTION` in `ConfigCI.psm1`).

## Known soft spots

- Emptiness, not malformed data, is where scripts break: seven shipped bugs came from fixtures with every field filled against an estate whose ordinary case is null. `@($null)` has `Count` 1, so a `Count -eq 0` guard on an unbound `[string[]]` never fires. A function's return unrolls down the pipeline, so `[byte[]]` can become `[object[]]` (both Azure collectors scanned nothing on an empty resource group). Read properties with `Get-OpsPropertyValue`, not dotted access, under strict mode.
- `$LASTEXITCODE = 0` inside a function creates a shadowing local a later native call never updates, so the exit code checked afterward reads as a constant; reset with `Set-Variable -Scope Global` (`Invoke-DiskSpaceReclaim.ps1`).
